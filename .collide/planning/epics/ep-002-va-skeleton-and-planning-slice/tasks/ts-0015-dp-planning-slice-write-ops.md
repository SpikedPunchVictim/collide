## Goal

The provider ops `setStatus`, `link`, `claim` and `unclaim` through protocol v0 `apply`. Every file write holds the per-root lock file (created only when absent and never without the writer's pid, by a hard link from a temp file holding it; a waiter retries for up to 15 s; a lock whose pid is dead is taken over, never by two waiters at once) and goes by temp file, `fsync` and rename, so a reader never sees half a file and two writers never interleave. Files are edited line by line, never by re-serializing the YAML. `apply` answers `ok` (the new task, its version, the files touched and `items[]`), `conflict` for a stale `version` (a hash of the file's content), or `refused`. `claim` records the claimant, named in the op's arguments, in `owners`. Creating items and their ids is `ts-0030-qw`, and where a write lands and `--commit` are `ts-0031-xu`.

## Success criteria

- `setStatus active` changes only that item's `status` line (`git diff`).
- Concurrent `setStatus` calls on one file all report what is on disk (the lock test).
- A lock file left by a dead writer is taken over, and two waiters on one stale lock never both take it.
- A kill between the temp write and the rename leaves the old file whole.
- A `claim` on an item that already shows an owner is refused, unless the claimant is that owner. `unclaim` clears the owner.
- `link` adds a `blocked-by` entry and changes only the `links` lines.
- A write with a stale `version` returns `conflict` and changes nothing.

## Tests

Write first: the `git diff` test for `setStatus`; N concurrent `setStatus` calls whose every result is true to the final file; a failpoint that kills the writer between temp write and rename; a stale lock with a dead pid, taken over by exactly one of two waiters; the claim refusal; `link`; the stale version.

- Lock: `<root>/.collide/planning/.write-lock`, holding `<pid>\n`, removed on release (release fails loudly if the file is not ours). It is placed by hard link, which is the exclusive create: the pid is written to a temp file `.write-lock.<pid>.<rand>.tmp` beside it (created `wx`, `fsync`ed), then `link(temp, lock)` fails with `EEXIST` when the lock exists, and the temp file is always removed. So the lock file never exists without its whole pid, however long its writer is paused, and the pid is never judged from a half-written file. The scan never reads it, and `.gitignore` lists `.collide/planning/.write-lock*` and `*.collide-tmp`. A waiter polls every 10 to 20 ms for 15 s, then throws an error naming the lock file and the holder's pid. `process.kill(pid, 0)` decides dead (`ESRCH`); `EPERM` is alive. A lock whose content is not `<digits>\n` (made or changed by hand) is never taken over: the waiter times out and the message says the file holds no pid. After it has the lock, the holder removes `.write-lock*.tmp` files whose embedded pid is dead (a killed writer's), and leaves those of live pids.
- Takeover race: deleting a lock that looked stale is guarded by a claim file `.write-lock.takeover`, placed the same way (temp file and hard link, pid). Only the claim's holder deletes a stale lock, and it re-reads the lock under the claim and deletes only if it is still stale. So when A and B both read one dead pid, whoever gets the claim first deletes the stale lock and releases the claim, and the other either fails to get the claim (and waits) or, once it has the claim, reads the lock again and finds the first one's live lock and leaves it. Plain "rename the stale lock away, then check" was not used: it has a hole, since B can rename away A's fresh live lock (A took over between B's read and B's rename), and restoring it leaves a window with no lock. Residual risk, stated: a waiter killed inside the claim's read-and-delete leaves a dead claim; that is cleared by a rename to a unique name and a delete, which has the same shape of race, and so needs a kill in that window plus two waiters clearing the dead claim at the same moment. The lock file itself is only ever placed by the exclusive link. The test runs six rounds of two waiter processes released at one instant on a dead-pid lock; each round has exactly one takeover and strictly alternating enter and exit.
- Writes: temp file `.<name>.<pid>-<random>.collide-tmp` in the item's directory (the scan reads only `.md`), same mode as the item, `fsync`, `COLLIDE_FAILPOINT=before-rename` kills the process with SIGKILL there (inert unless that variable names it; see the comment on `failpoint` in `write.ts`), `rename`, then `fsync` of the directory (skipped on Windows). The reply is built from reading the file back, still under the lock. A write first removes any `.<name>.*.collide-tmp` beside the item, since every temp file is made under the lock and one still there is a killed writer's.
- Line edits: only the `status:` line, the `owners` line (or the block list's lines for `unclaim`), or the `links` lines change, and every other byte is kept, CRLF included. Forms: `status: x` with optional quotes and a trailing comment; `owners: []` and `owners: [a, b]` (one line, no quotes inside), and a block list for `unclaim`; `links: []` becomes `links:` plus one entry, and a block of one-line `- { type: blocked-by, to: ... }` entries gets the new entry after the last one, with its indent. Anything else (a folded status, `links: [{...}]`, entries over several lines, a missing `owners` or `links` line for the ops that need one) answers `refused` naming the line. After the edit the frontmatter is parsed again and must equal the old one with only the intended field changed, else `refused` and nothing is written. A claimant is written bare when it is plainly text (`claude-sonnet`) and double-quoted otherwise.
- `version` is required: missing, null or empty answers `refused` ("needs the version you last read"), never a write over an unknown file. A `version` that differs from the file's hash answers `conflict` with the current task (with its body) and writes nothing. The hash is of content, so a file that goes A, B, A has A's version again; the version cannot tell that history apart.
- Decisions the plan leaves open: an op that would change nothing (the status it already has, a claim by the current owner, an unclaim with no owner, a link already stored) answers `ok` with `files: []` and `items: []` and writes nothing. `link`: a duplicate is that no-op; a link to the item itself is `refused`; a target that is no item the scan found is `refused`; the optional `type` argument may only be `blocked-by`; no cycle check. `setStatus` takes exactly one of `status` or `category` (the plan's "a `status` or a `category`"; every status is named after its category, so both take the same five values); both or neither is `refused`, and the schema says so with `oneOf`. `claim` takes `claimant` (1 to 200 characters, no control characters, no space at either end). No op declares `movesTo`: `setStatus` moves to whatever its argument names, and `claim` leaves the status alone. The ops are declared once in `initialize.ops`, not repeated in each kind. A `checkout` other than null or absent is `refused` for now, because where a write lands is `ts-0031-xu`; `--commit` is also that item's.
