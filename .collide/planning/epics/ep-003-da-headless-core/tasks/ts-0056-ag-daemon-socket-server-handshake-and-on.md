## Goal

The daemon (`host/src/daemon.rs`, `host/src/launch.rs`, `host/src/base_env.rs`): its entry, the socket server speaking the skeleton's JSON-RPC with the version handshake and the per-client token, the CLI token file at `0600`, on-demand start under the lock file with the `setsid` start, and the base environment captured at start and again when the app starts. Replaces the stubs tagged `daemon: entry`, `daemon: socket server`, `daemon: lock file start`, `daemon: setsid start` and `daemon: base environment`.

## Success criteria

- A daemon started from a terminal survives closing that terminal (Stage 3a criterion).
- Two starts at once give one daemon: the flock on the lock file serializes them, and a start waits up to 15 s (0.2, Starting the daemon).
- A client with no token or a wrong token is refused. A client with a different protocol version is refused at the handshake, with both versions in the message.
- The socket directory is `0700` and checked at start, and the token file is `0600`, made at the first start. A socket path over 103 bytes fails fast, naming the path and the limit (0.2, The socket).
- The base environment comes from `$SHELL -l -i -c` printing `env -0` between nonce markers, with stdin from `/dev/null`, under a timeout and capped at 1 MiB, in a session killed after reading. On failure it falls back to the minimal environment and logs why. `LANG` is set when missing. A new capture is used for new phases only (0.2, The base environment).
- A store that cannot be read is moved aside and reported at daemon start, using `ts-0053-gn`; the daemon keeps running.
- The daemon raises its soft open-file limit at start.
- The daemon's own log, written through a writer that fails with `ENOSPC` on demand, does not crash it: logging never panics (Stage 3a criterion; 0.2, Durability).
- No stub tagged `daemon:` remains except `daemon: launchd job` (`ts-0058-ad`) and `daemon: adopt shims` (`ts-0057-ck`).

## Tests

Write first: start, then a second start that finds the running daemon; two starts at once; token and handshake refusals; the long socket path; base-environment capture with a fake shell (nonce markers, a hung shell under the timeout, output over the cap); terminal close, in a test that starts the daemon from a child session and ends that session.

### Decisions for the owner

1. **The runtime is `std` threads, not tokio.** This item waits on a socket and nothing else; the plan's tokio is for reaping shims, which is `ts-0057-ck`. Alternative: tokio now, which adds a dependency and an async `auth` API for no gain yet. Recommend threads here and tokio where the reaping is, with the daemon's state behind the same `Shared` type. No new crate was added.
2. **Default locations (a new directory in the user's home; changes what the install leaves on a machine).** `DaemonPaths::for_home`: the socket, token and lock in `~/.collide/run` (mode `0700`), and the runs, the store and the log in `~/Library/Application Support/Collide`. The plan says only "a short fixed path". Alternatives: `/tmp/collide-<uid>` (shortest, but macOS cleans `/tmp`, which would delete a live daemon's token), `$TMPDIR` (about 49 bytes before the name, too long to rely on), everything under Application Support (the socket path is about 66 bytes for an ordinary user name and fails on a long one). Recommend as built; a home so long that `~/.collide/run/d.sock` passes 103 bytes fails at start with the path and the limit named, and `COLLIDE_DAEMON_ROOT` moves everything. Tests only ever use the override.
3. **`collide-daemon start` is the entry that starts a daemon (no new `collide` command).** The CLI, the app and a shim whose child ended all call `launch::ensure_daemon`; the binary's `start` argument is that call, and it is how the terminal test starts a daemon from a child session. Alternative: a `collide daemon start` subcommand, which is a new CLI surface (command tree, schemas, help). Recommend as built until Stage 3b wires `collide run` to `ensure_daemon`.
4. **A failed capture does not replace a good one.** On `daemon.recapture_environment`, if the login shell then fails or times out, the answer says `fell_back` with the reason and the daemon keeps the earlier capture from the login shell, since the minimal environment would lose a working `PATH`. The plan says only that a failure falls back to the minimal environment. Alternative: always use the newest, which makes one slow shell during a run's start drop `PATH` for the next phase. Recommend as built. **This changes product behaviour.**
5. **The capture runs on its own thread after the socket is bound**, so the daemon answers within milliseconds (the plan measured about 70 ms) and a login shell that takes seconds does not delay the start or the 15 s wait. Until the first capture ends, `Daemon::base_environment()` is `None`. Alternative: capture before binding, which delays every start by the shell's time. Recommend as built; Stage 3b's first phase must wait for the first capture (or take `None` as "capture now").
6. **A store that fails for a reason other than being unreadable refuses the start.** `StoreError::TooNew` (a store from a newer build) and an I/O failure end the start with the error (`SocketError::Store`) and leave the store as it is; only a store that cannot be read is moved aside and the daemon runs on a fresh one. `StoreHealth` has no "unavailable" state to report, and a daemon with no store cannot record anything. Alternative: run without a store and answer `unavailable`, which needs a new `StoreHealth` variant in `core`. Recommend as built.
7. **Every start is `setsid` for now, and returns `StartKind::SetsidFallback` with the plan's warning**, because the launchd job is `ts-0058-ad`'s. The CLI therefore prints the "may end with its launcher" warning on every start on macOS until that item puts the job first. Alternative: return a plain `Setsid` kind and stay quiet. Recommend as built, since the warning is true until the job lands.
8. **The daemon's log file grows without a cap.** The start appends the daemon's stderr to `daemon.log`; the plan gives caps for a child's lines and a phase's log, not for the daemon's. Alternative: a size cap with one rotated file. Recommend adding it in Stage 3b's hardening; it does not affect this item's criteria.
9. **A start counts the socket as answering when a connection is accepted**, not when a handshake passes. A handshake needs the token, which the starter would have to read; an accepted connection that sends nothing and closes is dropped quietly by the daemon. Alternative: probe with `daemon.status`. Recommend as built; the CLI's first call checks the version anyway.
10. **Limits the plan does not give, as constants:** a connection has `HANDSHAKE_WAIT` (10 s) to send `initialize`, at most `MAX_CONNECTIONS` (256) are served at once, a line is at most core's `MAX_MESSAGE_BYTES` (8 MiB), a write to one client may block 5 s, and the soft open-file limit is raised to `MIN_OPEN_FILES` (4096, held to the hard limit). All are single constants or options.
11. **`SIGHUP` is not ignored.** A daemon that is in its launcher's session by mistake should end with it, and the terminal test checks the session instead of relying on the hangup. Alternative: ignore it as defence in depth, which would hide a lost `setsid`. Recommend as built.

- Owner decisions (2026-11-15): the recommendations above are accepted as built. The default locations (`~/.collide/run`, `~/Library/Application Support/Collide`) are reported to the owner, since the plan's other user files are under `~/.config/collide` and `~/.cache/collide`; they live in `DaemonPaths::for_home` alone. During the build one test started a daemon against the real home before it was fixed; the files it made were removed by exact path and checked gone. Every daemon test now sets `COLLIDE_DAEMON_ROOT` and clears the environment. Follow-ups for Stage 3b: a cap on `daemon.log`, and the first phase waits for the first capture.
